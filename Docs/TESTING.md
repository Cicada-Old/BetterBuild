## 2. 测试方法

- **功能测试**：逐项执行操作并取证（界面读数、日志片段、截图），不靠「看起来正常」判断。
- **性能测试**：同一存档、同一负载、固定时长分段采样，比较「启用本模组」与「停用本模组」两组；同一配置重复多轮取中位或平均。
- **兼容性测试**：只与上表这套现有 mod 组合一起跑，不穷举、不预设第三方兼容清单。

## 4. 性能测试结果

**结论：未测出可测量的吞吐开销。** 具体口径如下，请连同边界一起看：

- 共九批、约 60 轮实测。×1 档各批差值在 **±0.3%** 内；×3 档多数 **±0.1%**；×6 档跨批次在 **−5.4% ~ +5.7%** 之间且**符号翻转**，幅度小于同侧轮间极差（7.7%）——因此判定为「测不出」，而不是「有 X% 开销」。
- TPS 在低速与中速档基本贴满速；高速档受 CPU 瓶颈影响，两组同时下降，差值不具单调性。
- FPS 与内存两组同量级，长时间运行内存无单调上升。
- 本模组的函数热点合计约 **0.26 ms/tick**（每 3900 tick 约 1.0 秒），其中材料预算重建占约 44%。
- 诊断日志在高速档 10 分钟约 700~750 条，有节流，不会刷屏。

**未覆盖的部分（必须说明）：**

1. 设计的 8 种「开关 × 环境 × 负载」组合只完成 4 种（高环境两组、纯净环境停用侧两组）。
2. 「纯净环境 + 启用本模组」一组**无效**：测环境搭建时第三方 mod 在启动阶段抛空引用，游戏自动重置了启用列表，本模组实际未加载。
3. 「纯净环境 + 启用本模组」的高压格**未跑**。
4. 更高倍率档（开发者加速档）**未测**：三个常规档未能压满 CPU，但用户决定不再加测。
5. 以上缺格经确认后结案；**结论的适用范围是「常规三档 + 高环境」，不外推到纯净环境启用侧**。性能九批的 mod 环境是 **207 个**（在 211 个的基础上临时停用 4 个改速度倍率的 mod，以保证按钮档就是原版 ×1 / ×3 / ×6）；功能与兼容性测试是 211 个。

## 5. 兼容性

- 与 211 个 mod 的现有组合一起加载：`missingMods` 为空、无本模组相关的加载失败。
- 启动日志 8804 行，其中 3 条 ERROR 全部来自第三方 mod；含本模组名称或日志前缀的行共 7 条，异常 **0** 条。
- 建造页、诊断页在该组合下均可正常打开与读数。
- 与 QualityBuilder 存在**协作关系**（品质建造修复会用到它的数据），不装也能正常使用其余功能。

## 6. 如何自己复现

1. 在 1.7 上启用 Harmony + 本模组，载入任意殖民地存档。
2. 打开「建造」入口，切换建造页与诊断页。
3. 造一批蓝图（同类型与不同类型都放一些），观察诊断页结论是否随材料变化。
4. 调「调度设置」里的保护期与老化期，观察预算与提权行为变化（保护期改动最迟 15 tick 生效）。
5. 需要看日志：`%USERPROFILE%\AppData\LocalLow\Ludeon Studios\RimWorld by Ludeon Studios\Player.log`，本模组的行以 `[BM]` 开头。
